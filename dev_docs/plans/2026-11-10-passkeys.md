# Passkeys

**Status:** Phase 1 built on `main` (V231), unreleased. All four decisions made on
2026-11-10 (see [Decisions](#decisions)). What changed while building is in
[As built](#as-built).
**Requested by:** the maintainer, 2026-11-10, after seeing passkeys offered on more and
more sites.
**Builds on:** the device cookie and new-country alert of the same day (V230,
`PhoenixKit.Users.LoginAlerts`), and on QR sign-in, whose shape the sign-in flow copies
(`PhoenixKit.Users.QrLogin`).

## As built

Phase 1 differs from the text below in these places, each found while building it.

- **No "sign in again" button for the 15-minute rule.** Sign-out cannot carry a
  destination, and adding one would change how the multi-session stack pops an
  account. The section says in words to sign out, sign in and come back. A proper
  step-up (confirm with the password or an existing passkey) belongs to Phase 2.
- **The admin's card is on the user page's Account tab**, below Registration
  Details, and is always remove-only, one's own user page included: that page has
  no session token, so it could never satisfy the fresh-sign-in rule anyway.
- **`wax_` starts a metadata process**, idle unless `:update_metadata` is set, so a
  host makes no network call because of it. Registration passes
  `verify_trust_root: false` (we keep no metadata, so there is no root to check).
- **Synced or not** is read from the backup-eligible flag and shown as "synced" /
  "this device only".
- **The login page's suggestions start on their own** when the browser offers
  conditional mediation; the button aborts them first. Chromium's virtual
  authenticator answers the suggestion request at once, which is how the
  end-to-end run proved that path without a click.
- **Proven in a real Chromium** (DevTools WebAuthn virtual authenticator) against
  the library's endpoint served over HTTP: add on the Security tab, sign in through
  the suggestion (it returned to the page the person had been sent from), and
  through the button.
- **The profile page gained a catch-all `handle_info/2`.** Sending the email from
  the page put the test mailer's message in its mailbox and crashed it; other
  LiveViews already had one.

## What and why

A passkey is a key pair the person's device makes for this site. The device keeps the
private key, behind Face ID, Touch ID, Windows Hello or the device PIN, and usually syncs
it through iCloud Keychain, Google Password Manager or a password manager. The site keeps
only the public key. To sign in, the site sends a random challenge, the device signs it,
and the site checks the signature.

What that gives us over what we have:

- **It cannot be phished.** The browser uses a passkey only on the domain it was made
  for. A look-alike page gets nothing, unlike a password typed into it or a magic link
  forwarded to it.
- **Nothing to leak or reuse.** A database dump holds public keys only.
- **One tap.** The browser can offer the passkey in the email field as the page loads
  (conditional mediation, "autofill"), so a returning person types nothing.
- **It checks the person, not just the device.** We require user verification, so every
  sign-in is something the person has (the device) and is or knows (biometric or PIN).

It is a fifth sign-in method beside password, magic link, QR and OAuth. All of them end
in `PhoenixKitWeb.Users.Auth.log_in_user/3`, so remember-me, `return_to`, the
new-login and new-country alerts, the email-confirmation gate, and the refusal of service
users and managed organizations (`log_in_user/3`'s `api_only or managed_by_members`
clause) apply to passkeys with no new code.

## Out of scope for Phase 1

- **Accounts with a passkey and no password** (sign up with a passkey). Phase 2.
- **A passkey as a second factor or to confirm a sensitive action.** Phase 2. Trusted
  devices belong there: "trusted" only means something once there is a check to skip.
- **Provider names from AAGUIDs** ("iCloud Keychain"). A passkey is named after the
  browser and OS it was made on; the person can rename it.
- **More than one domain per install.** One relying party, the canonical origin.

## Design

### The relying party (the domain a passkey belongs to)

`rp_id` is the host of `PhoenixKit.API.MCP.Origin.canonical_origin/0` (the `site_url`
setting, else the endpoint URL), and the expected origin is that origin itself. Never the
request's `Host` header: the same rule as the API's discovery documents.

⚠️ **A passkey works only on the domain it was made for.** A host that moves from
`old.example.com` to `example.com` loses every passkey. Password and magic link remain,
so nobody is locked out, but the person has to add their passkeys again. Each row stores
the `rp_id` it was made for, so:

- a passkey made for another domain is shown as "made for old.example.com, no longer
  usable" in the person's list, instead of silently failing;
- `mix phoenix_kit.doctor` warns when passkeys exist for an `rp_id` other than the
  current one;
- the guide and the Settings → Authorization description say so before an admin turns it
  on.

`localhost` counts as a secure origin, so development works over plain http.

### Library

[`wax_`](https://hex.pm/packages/wax_), the maintained Elixir WebAuthn library: it makes
challenges and verifies registration and authentication responses (CBOR, COSE keys,
attestation formats, flags). We accept attestation `none` and do not check authenticator
metadata (we do not limit which authenticators may be used). Pass `origin` and `rp_id`
per call, because `site_url` is a runtime setting. Check its exact function names and its
dependency tree against `mix prerelease` (`deps.audit`, `hex.audit`) before committing to
it.

### Data: `phoenix_kit_user_passkeys` (new core table)

| Column | Type | Notes |
|---|---|---|
| `uuid` | `uuid` PK | `uuid_generate_v7()` |
| `user_uuid` | `uuid` NOT NULL | FK `phoenix_kit_users`, `ON DELETE CASCADE`; indexed |
| `credential_id` | `bytea` NOT NULL | unique |
| `public_key` | `bytea` NOT NULL | COSE key, CBOR-encoded |
| `sign_count` | `bigint` NOT NULL DEFAULT 0 | see "Sign count" below |
| `rp_id` | `varchar(255)` NOT NULL | the domain it was made for |
| `transports` | `varchar(32)[]` NOT NULL DEFAULT `'{}'` | browser hint, e.g. `internal`, `hybrid` |
| `backup_eligible` | `boolean` NOT NULL | synced passkey (true) or device-bound |
| `name` | `varchar(100)` NOT NULL | default "Chrome on macOS" (`PhoenixKit.Utils.UserAgent`) |
| `last_used_at` | `timestamp(0)` | |
| `inserted_at`, `updated_at` | `timestamp(0)` NOT NULL | |

- New version of the chain (the next free number when this is built), prefix-safe per
  `dev_docs/guides/2026-07-27-prefix-safe-migrations.md`, with a manifest overlay made by
  a generator like `dev_docs/squash/generate_v229_manifest.exs` (a new table, not a
  hand-declared column) and a `VnnnTest` holding the manifest to the catalog.
- The table goes into `PhoenixKit.Migrations.ModuleOwnedTables`' core list.
- Schema `PhoenixKit.Users.Auth.Passkey` with `use PhoenixKit.SchemaPrefix`.
- **The user handle** (WebAuthn `user.id`, returned by the device at sign-in) is the 16
  bytes of the user's uuid: not personal data, no new column. Sign-in checks that it
  names the same user as the credential's row.

### Context: `PhoenixKit.Users.Passkeys`

- `enabled?/0`: setting `passkey_login_enabled`, default `false`.
- `registration_options/2` and `register/4`: make the challenge for a user; verify the
  device's answer against it and insert the row.
- `authentication_options/0` and `authenticate/2`: make a challenge with no
  `allowCredentials` (discoverable credentials, so no email is needed first); verify an
  answer, find the row by `credential_id`, check the user handle, update `sign_count` and
  `last_used_at`, return `{:ok, user}`.
- `list/1`, `rename/3`, `delete/3` (by an actor; see "Who may change them").
- Every refusal is one generic `{:error, :invalid}` to the caller (no "no such
  credential" versus "bad signature" oracle); the reason goes to the log through the
  usual rules (no challenge or credential bytes in a log line).

**Sign count.** Synced passkeys always report 0. A non-zero count that goes backwards can
mean a cloned key: we log it and record an activity entry, but do not refuse the sign-in
(the spec leaves this to the site; refusing locks out people whose authenticators
misbehave).

### Signing in

The sign-in page (`PhoenixKitWeb.Users.Login`) is a LiveView, so the flow copies QR
sign-in: the challenge never leaves the server, and the session is set by a controller.

1. On connected mount, when `Passkeys.enabled?/0`, the LiveView makes a challenge, keeps
   it in an assign (server memory; single use by construction), and pushes the options
   to a hook.
2. The hook starts conditional mediation (`navigator.credentials.get` with
   `mediation: "conditional"`), so the browser offers saved passkeys in the email field
   (`autocomplete="username webauthn"`). A **Sign in with passkey** button, beside "Sign
   in with Magic Link" and "Sign in with QR code", starts the modal form of the same
   call for browsers without autofill.
3. The hook pushes the answer to the LiveView. **Rate limit first**
   (`RateLimiter.check_passkey_login_rate_limit/1`, by `IpAddress`), before any lookup,
   as every public auth endpoint does. Then `Passkeys.authenticate/2`; the challenge
   assign is cleared whatever the result.
4. On success the LiveView mints a one-time sign-in token: a `phoenix_kit_users_tokens`
   row with context `"passkey_login"`, hashed, valid for 60 seconds. It navigates to
   `PhoenixKitWeb.Users.PasskeyLoginComplete` with that token and the page's `return_to`
   (`Routes.return_to_query/1`).
5. The controller consumes the token (one atomic `DELETE ... RETURNING`), then calls
   `log_in_user(conn, user, Auth.remember_me_params())`. Never a hardcoded
   `"remember_me" => "true"`.

The page's language, `return_to`, and the website gate behave as for the other methods.

### Adding and managing passkeys

A **Passkeys** section in the person's account settings (`/profile/settings/...`, next
to the password and Active Sessions):

- a list: name, made on (date), last used, "synced" or "this device only", and the
  "made for another domain" state;
- **Add a passkey**: the same LiveView-plus-hook pattern with
  `navigator.credentials.create`, `residentKey: "required"`,
  `userVerification: "required"`, and `excludeCredentials` set to the person's existing
  passkeys, so a device does not save a second one;
- rename and remove.

**Who may add one.** A passkey is a way back into the account for as long as it exists,
so adding one is the persistence an intruder wants:

- only from the person's own session: refused while impersonated
  (`MultiSession.impersonated?/1`) and while acting for an organization;
- only from a fresh sign-in: the session token is younger than 15 minutes (decision 3),
  otherwise the section offers "Sign in again to add a passkey", which signs in and
  returns here through `return_to`;
- checked in the event handler, not only by hiding the button (the forged-event test
  pattern of Settings -> API).

**Telling the person.** Adding or removing a passkey sends a security email ("A passkey
was added to your account", new `passkey_added` / `passkey_removed` templates in
`CoreTemplates`, the recipient's language, `User.delivery_email/1`) and an in-app
`security` notification, and logs `user.passkey_added` / `user.passkey_removed`. Signing
in logs the method in the existing sign-in activity.

**Admins.** A user's admin page lists their passkeys and can remove them (account
recovery, a lost phone), under the rank rule used for ending sessions
(`Sessions.can_revoke_sessions_of?/2`). An admin can never add one for someone else.

### Settings

- `passkey_login_enabled` (default `false`) on Settings → Authorization, beside QR
  sign-in. It goes into `@public_setting_keys` and `@security_setting_keys` (a
  `settings.security` key, like every sign-in method).
- Off means: no button, no autofill, the Passkeys section hidden, and `authenticate/2`
  refuses. Stored passkeys stay, and work again when it is switched back on.

### Browser code

A hook in `priv/static/assets/phoenix_kit.js` (core's own JavaScript, never an inline
`<script>`): feature detection (`window.PublicKeyCredential`,
`PublicKeyCredential.isConditionalMediationAvailable()`), base64url conversion both ways,
and the two calls. The conditional request is cancelled with an `AbortController` before
the modal one starts, and when the hook is destroyed. JS tests for the conversion and the
abort handling run in `mix precommit`. A host gets it through `mix phoenix_kit.update`
(say so in the CHANGELOG).

## Tests

- **A software authenticator in `test/support`.** It makes an ES256 key pair and builds
  real registration (attestation `none`) and assertion responses, so the integration
  tests exercise the real verification, not a stub.
- **Context:** register and sign in; wrong origin; wrong `rp_id`; a replayed challenge;
  another user's credential presented with a mismatching user handle; a sign count going
  backwards (signs in, logged); switched off.
- **Sign-in flow:** rate limit before lookup; a service user and a managed organization
  are refused; the one-time token works once and expires; `return_to` survives; the
  new-login alert runs.
- **Settings:** forged `add` events while impersonated, while acting for an organization,
  and from a stale session are refused; the email goes out on add and remove; an admin
  removes but never adds; the rank rule.
- **Migration:** a `VnnnTest` (round trip, manifest against catalog) and the prefix
  oracle `test/integration/prefix_migration_test.exs`.
- **In a real browser:** Chromium's virtual authenticator (DevTools protocol
  `WebAuthn.addVirtualAuthenticator`) through the playwright setup that already works
  here, end to end: add a passkey in settings, sign out, sign in through autofill and
  through the button.
- **Strings** in all nine translated languages, 0 fuzzy.

## Phases

1. **Phase 1: sign in with a passkey.** Everything above.
2. **Phase 2, later:** accounts with a passkey and no password; a passkey to confirm
   sensitive actions (email change, adding API keys) instead of the password; trusted
   devices and "Forget this device" in Active Sessions, built on the V230 device cookie.

## Decisions

Made by the maintainer on 2026-11-10, each as proposed.

1. **The switch is off by default**, like QR sign-in. A host turns it on when its
   `site_url` is final.
2. **Admins can remove a user's passkeys in Phase 1.** Without it a lost phone means the
   person cannot clean up their list until they sign in another way.
3. **Adding a passkey needs a sign-in from the last 15 minutes.**
4. **The password stays required in Phase 1.** It is the way back after a domain change
   or a lost device; accounts without one are Phase 2.
