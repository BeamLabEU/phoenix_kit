## 1. The idea

Long background work in PhoenixKit has no common shape. A backfill, a reconcile pass, a library
purge — and tomorrow a newsletter broadcast, an import, a sitemap rebuild — are each an Oban worker
that chains itself batch by batch. The admin can see raw Oban rows and cannot tell what a piece of
work *is*, how far along it is, who started it, or stop it.

The plan: a **run** is a durable record of one logical piece of work. Oban stays the executor — each
Oban job is one *batch* of a run — and the run is what an admin watches and controls. Pause, resume,
cancel and retry are state changes on the run; the worker reads the state before every batch and
before it queues the next, so a paused or cancelled run simply stops emitting work.

It is **universal**: any module declares kinds of run, and the Jobs section lists and controls them
all. Media storage is the first customer because it has the pain today (no per-library state, no way
to check, pause or see what happened), but nothing in the engine is storage-specific.

Three things the maintainer asked for, and where each lands:

| Ask | Where |
|---|---|
| A state for each library, and a way to check/rebuild it by hand | §6 (library state, Check now) |
| A place to see jobs, their progress, and start/pause/stop/cancel them | §3–§5 (the engine, the Runs tab) |
| History: who changed what, who ran, paused, cancelled | §7 (Activity log) |

## 2. What exists today (verified in the tree, 2026-10-03)

- **Three layers, only two exist.** (a) Oban, the executor. (b) `PhoenixKit.ScheduledJobs`: a table
  (`phoenix_kit_scheduled_jobs`), a `Handler` behaviour and a per-minute cron worker — "run this
  once at time T" (a post publishing). Status, attempts, cancel; no progress, no pause. (c) What is
  missing: long, multi-batch work you can watch and control.
- **The Jobs page** (`/admin/jobs`, `PhoenixKitWeb.Live.Modules.Jobs.Index`) has two tabs: the raw
  Oban jobs table (queue/state/worker filters, 30 s refresh, read-only) and the scheduled jobs. It
  is gated by the module toggle `jobs_enabled`, **off by default**.
- **`PhoenixKit.Jobs` is a `PhoenixKit.Module`** (`module_key "jobs"`, listed in
  `ModuleRegistry.internal_modules/0`, in `Modules`' `@internal_module_keys`, with a card and toggle
  in `modules.html.heex`, and an admin tab with `permission: "jobs"`). The permission key `jobs` is a
  *feature* key, not one of `Permissions.core_section_keys/0`
  (`dashboard users media settings modules`).
- **20 Oban workers** in core (prunes, digests, notification delivery, sitemap scheduler, storage).
  The storage maintenance workers — `ReconcileJob`, `LocationBackfillJob`, `ChecksumBackfillJob`,
  `CaptureDateBackfillJob` — are all the same hand-written pattern: one batch per run, the next
  scheduled with a cursor, `unique` over `[:worker, :queue]` so one pending pass exists, queued after
  boot and by the daily `PruneTrashJob`. `PurgeLibraryJob` is a single job per library.
- **Oban is the open-source edition** (`{:oban, "~> 2.20"}`). It can pause a *queue* (which would
  also stall upload processing: `file_processing` is shared), cancel a job, and snooze. It cannot
  pause one job. The installer configures `Oban.Plugins.Pruner` (30 days), `Oban.Plugins.Lifeline`
  (rescues jobs orphaned in `executing`) and `Oban.Plugins.Cron`.
- **`Reconciler.run_batch(cursor, limit, totals)`** already walks `stale_query/0` in uuid order. It
  has a global `stale_count/0` and the Health page lists stale files; there is no per-library count
  or state.
- **The Activity log** (`PhoenixKit.Activity.log/1,3`, feed at `/admin/activity`, filters by module,
  mode, action, user, resource type, date; retention `activity_retention_days`, default 90) exists
  and storage barely writes to it. The feed page is gated by `dashboard` access.

## 3. The model

> **Read §14 with this section.** Codex's review (§13) found real gaps in §§3.2–3.6 — uniqueness
> does not serialize execution, completion needs an atomic protocol, recovery can reset the failure
> budget, the batch callback cannot checkpoint and delay together. §14 is the revised protocol and
> overrides this section where they differ.

### 3.1 A run

Table `phoenix_kit_job_runs` (V207):

| Column | Meaning |
|---|---|
| `uuid` | UUIDv7, primary key |
| `kind` | the registered kind, `"storage.reconcile"` |
| `module` | the module key that declared it (`"media"`), for the Activity log and permissions |
| `scope_type`, `scope_uuid` | what the run is about: `"library"` + uuid, or both nil for the site |
| `title` | a human title fixed at start ("Reconcile Media") — never recomputed from live data |
| `state` | `queued` · `running` · `paused` · `completed` · `failed` · `cancelled` |
| `done`, `total`, `failed_count` | progress counters; `total` nil when unknown |
| `cursor` | jsonb, where the next batch resumes |
| `args`, `result` | jsonb: what it was started with; a summary when it finishes |
| `error` | text, the last failure |
| `mode` | `manual` · `auto` · `cron` · `script` (the Activity log's vocabulary) |
| `started_by_uuid` | the actor, nil for automatic runs |
| `paused_by_uuid`, `paused_at`, `cancelled_by_uuid`, `cancelled_at` | who and when |
| `restart_requested` | a trigger arrived while it ran (§3.4) |
| `heartbeat_at` | set by every batch; the sweeper's evidence of life |
| `inserted_at`, `started_at`, `finished_at`, `updated_at` | |

A **partial unique index** on `(kind, coalesce(scope_type,''), coalesce(scope_uuid, nil-uuid))`
`WHERE state IN ('queued','running','paused')` — at most one *active* run per kind and scope, which is
what makes "start" idempotent.

No foreign keys to scope tables: a run must outlive what it was about (a purged library), the same
choice V206 made for `owner_uuid`.

### 3.2 States and transitions

```
        start              batch ok / more
 (none) ───▶ queued ───▶ running ◀──────────┐
                │           │ │ │           │
                │           │ │ └───────────┘
        cancel  │   pause   │ │ done            fail (max attempts / kind error)
                ▼     ▼     │ ▼                  ▼
            cancelled  paused  completed        failed
                         │ resume ▲                │ retry
                         └────────┘                └──▶ queued
```

- **pause** is cooperative: the batch in flight finishes (up to the kind's timeout — 30 minutes for
  storage, where a batch may transcode video, **not** "a few seconds"; the two seconds are the delay
  *between* batches), the worker sees the request and does not queue the next. Killing a batch
  mid-file is what Oban's cancel does and nothing here wants it. While a batch drains the run is
  `pausing` and the UI says so (§14 R1, R6).
- **resume** sets `queued` and enqueues the next batch from `cursor`.
- **cancel** sets `cancelled`, cancels the run's pending Oban job (`Oban.cancel_job`) and stops. A
  batch already executing finishes; it does not start another.
- **retry** is for `failed` (and `cancelled`): a new run of the same kind and scope with the old
  `args`, linked in `result` — never a mutation of a finished row, so history stays true.
- Every transition takes the **actor** and writes an Activity entry (§7).

### 3.3 A kind

A behaviour, `PhoenixKit.Jobs.Kind`:

```elixir
@callback kind() :: String.t()                          # "storage.reconcile"
@callback title(run) :: String.t()                      # "Reconcile Media"
@callback batch(run) ::
            {:more, %{cursor: map(), done: integer(), total: integer() | nil, failed: integer()}}
            | {:done, result :: map()}
            | {:error, reason}                           # counts against the Oban attempt
            | {:retry_in, seconds}                       # a pause between batches (throttle)
@optional_callbacks [
  queue: 0,            # default :default; storage kinds use :file_processing
  max_attempts: 0,
  on_start: 1,         # may refuse: {:error, :nothing_to_do}
  on_finish: 2,        # (run, final state) — tidy up
  restart: 0,          # :restart (a trigger resets the cursor) | :merge (default)
  permission: 0        # extra permission needed to control it, e.g. "media.manage"
]
```

Modules declare their kinds the way they already declare `email_templates/0` and `oban_queues/0`: an
optional `PhoenixKit.Module` callback `job_kinds/0` (default `[]`), collected by
`ModuleRegistry.all_job_kinds/0`. Core kinds that belong to no module are registered in core.

### 3.4 Start, restart, merge

`Jobs.start(kind, scope, opts)` — `opts`: `args`, `mode`, `actor_uuid`.

- No active run for `(kind, scope)`: insert `queued`, enqueue the first batch, log it, broadcast.
- An active run exists: the kind's `restart/0` decides. **`:merge`** (default) returns the existing
  run and does nothing. **`:restart`** sets `restart_requested`; the worker, at its next batch
  boundary, resets `cursor`/counters and carries on — which is what `ReconcileJob` does today
  ("a change queued while a pass is under way starts the walk again from the beginning").
- Concurrent callers race on the partial unique index; the loser reads the winner.

### 3.5 The worker

One generic `PhoenixKit.Jobs.RunWorker` (queue taken from the kind; `unique` on `run_uuid` over
`available/scheduled` so a run has at most one pending batch):

1. Load the run. `cancelled`/`completed`/`failed` → `:ok`. `paused` → `:ok` (nothing queued).
2. If `restart_requested`, reset and clear it.
3. Mark `running`, set `started_at` once, touch `heartbeat_at`.
4. Call `kind.batch(run)`.
5. `{:more, p}` → persist progress and cursor, broadcast, **re-read the state** (it may have been
   paused or cancelled during the batch) and only then enqueue the next batch (`schedule_in` for
   `retry_in`).
6. `{:done, result}` → `completed`, `finished_at`, log, broadcast. `{:error, _}` → Oban retries
   the batch; on the last attempt the run is `failed` with `error`.

Counters are written **per batch**, not per file (storage batches are 10–50 files), so progress is
cheap and bounded.

### 3.6 Orphans and a dead queue

- **A sweeper** (cron, every few minutes, one node via Oban's peer/advisory lock)  *(revised by §14 R5)*: a run in
  `running` whose `heartbeat_at` is older than a threshold *and* which has no Oban job in
  `available/scheduled/executing/retryable` is re-enqueued (up to N times, then `failed` with
  "lost"). A `queued` run with no Oban job is enqueued. This is the run-level twin of Lifeline,
  which only rescues the Oban row.
- **Oban not running** (a web-only node, a config with `queues: false`): runs stay `queued`. The
  Runs tab says so ("no queue is running these") by checking Oban's config, rather than showing a
  run that looks alive.
- **Test and script mode:** `Jobs.run_inline(kind, scope, opts)` drives batches in the calling
  process (what `mix phoenix_kit.storage.backfill_capture_dates` does by hand today).

### 3.7 Progress and live updates

`PhoenixKit.PubSub.Manager` topics `phoenix_kit:job_runs` (any change) and
`phoenix_kit:job_runs:<uuid>`. The Runs tab subscribes and patches rows; the 30 s polling goes away
for runs. Broadcasts happen on transitions and on batch progress, so a busy run is a few messages
per minute, not per file.

### 3.8 Retention

`job_runs_retention_days` (default 90, like Activity). A daily prune deletes finished runs older
than that; active runs are never pruned.

## 4. Jobs becomes core, always on  *(decided)*

Maintainer's decision, 2026-10-03: **remove Jobs from Modules and always enable it.**

What that is, concretely:

- `PhoenixKit.Jobs` stops being a `PhoenixKit.Module`: drop it from
  `ModuleRegistry.internal_modules/0`, from `Modules`' `@internal_module_keys`, delete the card and
  toggle in `modules.html.heex`. The admin tab moves to the core admin tab list (like Activity).
- The module becomes the **engine's public context** (`Jobs.start/3`, `pause/2`, `resume/2`,
  `cancel/2`, `retry/2`, `list_runs/1`, `get_run/1`, `run_inline/3`). `enabled?/0` remains as a
  deprecated function that returns `true`; `enable_system/0` / `disable_system/0` are no-ops for
  one release, then removed. The `jobs_enabled` settings row is ignored (left in place).
- The `Jobs.Index` LiveView drops its "module disabled" redirect.
- **Permission key `jobs` stays** (so every role that holds it keeps it) and becomes a **core
  section key** (`Permissions.core_section_keys/0`), so `feature_enabled?("jobs")` is always true.
  The V53 seed that granted it is unchanged.
- New sub-permission **`jobs.manage`** (pause, resume, cancel, retry, start). `jobs` alone is
  *view*. **Not backfilled** (revised, §14 R3): the Jobs page is read-only today, so holders of
  `jobs` can only look; giving them control would *add* authority, unlike the `media` sub-permissions,
  which preserved what holders already had. A kind may require more (`permission/0`): controlling a
  storage run needs `media.manage` too.
- ⚠️ The Activity feed is gated by `dashboard`, not `jobs`. A role with `jobs` but not `dashboard`
  sees runs and their per-run history on the Jobs page (which reads the log itself) but not the
  global feed. Not changed here.

## 5. The Jobs page

`/admin/jobs` keeps its URL, gets three tabs (URL-backed, `UrlTabs`):

- **Runs** (default). Filters: module, kind, state, scope (library). Rows: title, kind, state
  badge, a progress bar (`done`/`total`, or an indeterminate bar when `total` is nil), started by
  and when (or "automatic"), duration, and an actions menu: Pause · Resume · Cancel · Retry (only
  what the state allows and the viewer may do). A run opens a drawer: facts, counters, the error,
  the cursor (admin only), its Oban jobs, and **its history** (the Activity entries of this run).
  Live over PubSub.
- **Queue** — today's Oban table, renamed, unchanged (debugging).
- **Scheduled** — today's tab, unchanged. A scheduled job may *start a run*: the two layers
  compose (`Handler.execute/2` calls `Jobs.start/3`).

State badges: Queued, Running, Paused, Completed, Failed, Cancelled — the daisyUI conventions the
admin already uses. Control buttons use `<.save_button>`-style confirmation (`data-confirm`) for
cancel; pause/resume are immediate and confirmed by the row changing.

## 6. Storage as the first customer

### 6.1 Kinds

| Kind | Scope | Replaces |
|---|---|---|
| `storage.reconcile` | library | `ReconcileJob` (one global walk) |
| `storage.location_backfill` | site | `LocationBackfillJob` |
| `storage.checksum_backfill` | site | `ChecksumBackfillJob` |
| `storage.capture_date_backfill` | site | `CaptureDateBackfillJob` |
| `storage.purge_library` | library | `PurgeLibraryJob` |
| `storage.verify` *(later)* | library | — (new, §10) |

`ProcessFileJob`, `ApplyImageEditJob`, `AnnotationThumbnailJob`, `DeleteOrphanedFileJob` and the
prune jobs stay plain Oban: one file per job, nothing to watch as a whole. `PruneTrashJob` keeps
running daily, and calls `Jobs.start/3` where it calls `maybe_enqueue/0` today.

### 6.2 Reconcile is per library

The reconciler's pass is today one walk over every stale file. A run per **library** is what makes
"state of a library", "check this library" and "pause this library" mean something, and a site has
few libraries.

- `Reconciler.stale_query/0` gains an optional `library_uuid` (nil = Media's, as everywhere).
- A **trigger** — a profile or variant-set revision bump, a library moving profile, an upload that
  made fewer copies — becomes `Reconcile.trigger/1`: for each library that has stale files, start
  its run (`restart: :restart`, mode `auto`). The existing `ReconcileJob.enqueue/0` call sites call
  this instead.
- `Reconcile` `batch/1` is `Reconciler.run_batch(cursor, 10, totals)` for the run's library, with the
  existing two-second throttle as `{:retry_in, 2}`.
- A manual **Check now** on a library is `Jobs.start("storage.reconcile", {:library, uuid},
  mode: "manual", actor_uuid: …)`.

### 6.3 Library state (derived, not stored)

One grouped query (stale files per library) plus the library's active/last reconcile run:

| State | When |
|---|---|
| **In sync** | no stale files, no active run |
| **Syncing** | stale files and a `queued`/`running` run — "N files left" |
| **Paused** | its run is `paused` |
| **Needs attention** | its last run `failed`, or files the reconciler keeps failing on (`reconcile_attempted_at` inside the retry window) |
| **Waiting** | stale files and **no** run (the queue is down, or nothing has triggered yet) — the case today's Health count hides |

Shown as a badge with the count on the **Libraries** tab, with **Check now**, **Pause/Resume** and a
link to the run. The Health page's global number stays.

### 6.4 What the stale test does and does not catch

Stale detection is **revision-based**: a bucket added or removed, a role changed, a copy count
changed — all bump the profile revision, and `Reconciler` rebuilds (copies are verified when made;
it never unlinks without a good copy elsewhere). It does **not** notice a bucket that silently loses
objects or goes away without an admin action. That needs `storage.verify` (HEAD each recorded
object, mark missing locations, make the file stale) — a separate kind, §10.

## 7. History

**Decision: the Activity log is the history store.** No second events table.

- Every run transition: module = the kind's module key (`"media"`), action
  `job.started|paused|resumed|cancelled|completed|failed|retried`, `resource_type: "job_run"`,
  `resource_uuid: run.uuid`, `mode` and `actor_uuid` as given, metadata `kind`, `scope`, `done`,
  `total`, `error`. Automatic runs are logged `mode: "auto"` with no actor — "who ran it" is the
  system, and that is visible.
- **Storage configuration changes** (the "who changed what" half): profile created/renamed/deleted,
  copy counts, a bucket added/removed/changed in a profile (role, stores, order, status — from → to),
  a library's profile / variant set / annotated-thumbnails choice, a bucket created/enabled/disabled/
  deleted, variant set and size changes. The contexts take `opts[:actor_uuid]`; LiveViews pass
  `PhoenixKitWeb.Actor.opts(socket)`. Actions: `storage.profile.updated`, `storage.library.profile_changed`,
  …, written through one small `Storage.Audit` module so the names live in one place.
- **Where it shows.** The run drawer shows its own entries. Settings → Media gets a **History** tab:
  the Activity list, prefiltered to the media module's storage actions, newest first. The list is
  extracted from `Activity.Index` into a reusable component rather than duplicated; the full feed
  stays at `/admin/activity`.
- Retention follows `activity_retention_days`. A run's own row lives `job_runs_retention_days`.

## 9. Compatibility and rollout

- **In-flight old jobs.** A host upgrading may have `ReconcileJob`/backfill jobs queued. The old
  workers stay for one release with their old `perform/1` clauses; each one **starts the matching
  run and returns `:ok`** (the old cursor is dropped — a pass restarts, which is safe: the reconciler
  and backfills are idempotent). They are removed the release after.
- **Cron entries.** Hosts' `Oban.Plugins.Cron` crontabs name `PruneTrashJob`, `ProcessScheduledJobsWorker`,
  digest workers. None of those change name. The sweeper and the runs prune are added to the
  installer's cron entries the way `ensure_digest_cron_entries/2` does, and `mix phoenix_kit.update`
  backfills them into existing hosts (a missing entry would leave orphaned runs unrescued — the same
  failure shape as the digest worker's).
- **Sibling modules** stay on `~> 2.0`: they feature-detect (`function_exported?(PhoenixKit.Jobs,
  :start, 3)` after `Code.ensure_loaded?/1`) and keep their own worker until their floor is raised.
- **Queues.** A kind's queue must be declared on the host (`oban_queues/0` already does this for
  modules); the storage kinds use `file_processing`, which every host has.

## 10. Out of scope (recorded)

- Moving **email broadcasts**, imports/exports, sitemap rebuild and digests onto runs: they are the
  reason the engine is universal, and each is its own piece of work after the engine ships.
- **`storage.verify`** (HEAD every recorded object): needs the engine first, and a decision about how
  often and how much egress is acceptable on remote buckets.
- **Pausing an executing batch mid-file** (Oban OSS cannot; the batch is short).
- A **cron editor** in the UI, priorities, rate limits (Oban Pro territory).
- **Failure notifications** (a run failed → the Notifications system): the Activity entry is the hook
  to add it on later.
- Changing who can read the global Activity feed.

## 11. Risks, and questions for the reviewer

| Risk | Closed by |
|---|---|
| A run says `running` and nothing is working | heartbeat + sweeper + Oban-state check (§3.6) |
| Two nodes drive one run | `unique` on `run_uuid`, the state re-read before enqueueing, the partial unique index on active runs |
| A control action outruns the permission model | `jobs.manage` + the kind's `permission/0`, checked in `Jobs.*`, not only in the LiveView |
| Progress broadcasts flood the socket | per batch, not per file |
| A restart storm (profile edited ten times) | `:restart` merges into `restart_requested`; one cursor reset per batch boundary |
| The migration breaks a prefixed install | the prefix-safe rules, the integration oracle, the manifest check |
| Hosts without the new cron entries | `mix phoenix_kit.update` backfill; the Runs tab flags "no sweeper seen" |

Questions I would like a second opinion on:

1. **Per-library reconcile runs** (§6.2) versus one site run with per-library counters. The first
   makes pause/check per library natural; the second is closer to today's code. Is the fan-out worth
   it?
2. **Cooperative pause** — is "the in-flight batch finishes" acceptable for a 10-file, ~2 s batch,
   and is there a failure mode in re-reading the state between the batch and the next enqueue?
3. **The sweeper's rule** (heartbeat stale *and* no live Oban job): can it resume a run that is
   merely slow? What threshold, given `Lifeline`'s `rescue_after`?
4. **Activity log as the only history** (§7): is 90-day retention and the `dashboard` gate right for
   an audit of who paused a library, or does this want its own events table?
5. **`jobs` as a core key** and the `jobs.manage` backfill: any path by which a role gains control
   it did not have?
6. **Naming**: "Runs" for the tab and table versus "Jobs". The page is already "Jobs"; Oban's rows are
   "Queue" in this plan.

## 13. Codex review — 2026-10-03

**Reviewer: Codex.** This section is feedback on Claude's proposal above, checked against the
current implementation and Oban documentation. It does not amend the decisions in §§1–12.

**Assessment:** the separation between a durable logical run and Oban batch execution is sensible.
Per-library controls, an extensible kind registry and reusing Activity are worthwhile. Revise the
concurrency, authorization and failure contracts before implementing Phase 1; the current risk table
claims guarantees that its proposed mechanisms do not establish.

### 13.1 Findings requiring a plan revision

#### C1 — HIGH: job uniqueness does not serialize execution (§§3.2, 3.5, 11)

The proposed uniqueness states exclude `executing` and `retryable`. A concrete overlap:

1. Batch A is executing and has not committed its next cursor.
2. A user pauses the run, then immediately resumes it.
3. Resume enqueues batch B from the persisted, old cursor; A does not prevent that insertion.
4. A and B can process the same batch concurrently.

Cancel followed by retry has a similar problem across **different run UUIDs**: cancellation releases
the partial active-run index while the old batch is still performing side effects. A lock only on
the run UUID would not prevent the replacement run from overlapping it. `run_inline/3` must obey
the same execution rules and must not race an automatically enqueued worker.

Specify an execution claim that serializes work for the same kind/scope, its crash-release or
recovery behavior, and a batch token/generation that rejects obsolete deliveries. Resume must not
drive a second batch while the previous one is draining. The partial index remains useful for
idempotent starts, but is not an execution lock.

Oban explicitly says uniqueness applies at insertion and does not control concurrent execution:
[Unique Jobs, locked Oban version 2.24.1](https://oban.hexdocs.pm/2.24.1/unique_jobs.html).

#### C2 — HIGH: completion and controls need an atomic protocol (§§3.4–3.5)

Re-reading state before enqueueing leaves a race between the read and the insert. The `:done`
path also does not say what happens when cancellation or a restart arrives during the final batch:
an unconditional completion write could replace `cancelled` with `completed`, or finish without
processing the new stale work that requested a restart.

Define precedence for completion versus pause/cancel/restart. Under a row lock or an equivalent
conditional-write protocol, commit the checkpoint, the next Oban job when needed, and any transition
history together. Broadcast after commit. A restart must be checked at the completion boundary too;
clearing its flag must not erase a newer trigger. A recovered old Oban job must not consume a newer
checkpoint as though it were its own batch.

Also document the kind's side-effect contract: a crash after external work but before its checkpoint
can replay that work. Storage's idempotent passes are a good first customer; future broadcasts and
imports need their own replay protection.

#### C3 — HIGH: the backfill gives existing viewers new authority (§§4, 8)

The current Jobs context and page principally expose a viewing interface. Backfilling `jobs.manage`
to every holder of `jobs` grants new start/pause/cancel/retry powers. The claim that this means
"nothing changes for existing roles" is incorrect. The media sub-permission precedent preserved
abilities those holders already had; this backfill introduces abilities.

Recommendation: existing custom roles keep view access and receive control access through an
explicit grant. If a blanket expansion is intended, record that as a maintainer decision with its
effect spelled out. Account for `Permissions.auto_grant_new_keys_to_admin/0`, which already grants
new sub-permission keys to Admin, as well as the migration seed.

#### C4 — HIGH: authorization cannot be reconstructed from an actor UUID (§§3.4, 4, 11)

`Jobs.start/3` lists only `args`, `mode` and `actor_uuid` options, while the plan promises checks in
the context. An actor UUID identifies a user, not the role active in their session. Reloading by UUID
can silently authorize against a different effective role.

Pass the current `%PhoenixKit.Users.Auth.Scope{}` for user controls, check `jobs.manage` and the
kind-specific permission against it, and derive audit attribution from it. Define a separate,
explicit trusted-system calling convention for boot, cron and scripts. An omitted actor or a
caller-supplied `mode: "auto"` must not implicitly establish permission to act as the system.

Reference: `Scope.for_user/2` in `lib/phoenix_kit/users/auth/scope.ex` narrows permissions to the
active role carried by the session-loaded user.

#### C5 — MEDIUM: recovery can reset the failure budget indefinitely (§§3.5–3.6)

Returned errors can be recorded on the final attempt, but a timeout, process death or Lifeline
discard can occur without `RunWorker` recording `failed`. The sweeper then sees no live Oban job
and may insert a new one with a fresh attempt budget. The promised "up to N times" rescue count
has no field or other durable representation in the proposed model.

Specify reconciliation of terminal Oban states, durable rescue counting, and the difference between
a lost dispatch and an exhausted batch. Exhausted work must become a failed run rather than restart
indefinitely. Keep the sweeper's no-live-job guard; a stale heartbeat alone does not justify rescue.
Lifeline itself may rescue a genuinely executing job, so execution claims remain necessary.

The installer currently chooses a 60-minute Lifeline threshold above core's longest 30-minute
worker timeout. A run sweeper every few minutes is reasonable for genuinely missing jobs; its
threshold must not substitute for that Oban-state check.
[Lifeline documentation](https://oban.hexdocs.pm/2.24.1/Oban.Lifeline.html).

#### C6 — MEDIUM: storage batches are not reliably short (§§3.2, 6, 10–11)

The two seconds are the delay **between** reconcile batches, not the time to execute ten files.
`ReconcileJob.timeout/1` allows 30 minutes and its source explicitly notes that video transcodes
take minutes. Cooperative pause is acceptable, but show "pause requested; current batch finishing"
until the execution claim drains, rather than implying work has already stopped.

Purge needs actual batching too: `Libraries.do_purge/1` currently loads and walks the whole library.
Define how pausing/cancelling interacts with the library's `purging` marker and its refusal to
restore. Cancellation cannot undo files already deleted.

Preserve cooperative cancellation when manipulating Oban rows: `Oban.cancel_job/2` kills an
executing job, and a previously pending job can become executing before cancellation reaches it.
Specify a mechanism that leaves the executing batch to drain.
[Oban cancellation documentation](https://oban.hexdocs.pm/2.24.1/Oban.html#cancel_job/2).

#### C7 — MEDIUM: the callback cannot return progress and a delay together (§§3.3, 6.2)

`{:more, progress}` checkpoints work, while `{:retry_in, seconds}` carries no cursor or counters.
Reconcile needs to checkpoint a completed batch **and** delay its successor.

Use a return shape such as `{:more, progress, schedule_in: 2}`. Reserve a separate retry/snooze
shape for work that made no checkpoint. Define whether `done`/`failed` are cumulative or increments,
how the final batch updates counters, and the replay guarantees of `on_start`/`on_finish`. Preserve
the existing workers' timeout behavior through a kind callback or another explicit policy.

#### C8 — MEDIUM: runnable stale counts cannot describe full library health (§6.3)

`Reconciler.stale_query/0` excludes recently attempted files, pending edits and some processing
files. It is a work-selection query. Reusing it as the health count can hide outstanding work,
especially once the ten-minute failure window expires without another run starting.

Separate "out of date" from "eligible for reconciliation now" and account for failed/deferred
files when deriving the badge. Prefer **Up to date** over **In sync** while object verification is
out of scope: matching revisions does not prove that every recorded object still exists.

### R1 — Execution is claimed, dispatch is generational, and pause/cancel drain (C1, C6)

Uniqueness stays for **idempotent starts only**; it is not an execution lock.

New columns: `generation` (int), `claim_token` (uuid, nullable), `claimed_at`, `oban_job_id`
(the current dispatch), `rescues` (int), `last_rescued_at`.

- **One dispatch per generation.** Every dispatch (start, resume, checkpoint successor, sweeper
  rescue, retry) increments `generation` and inserts the Oban job with `generation` in its args,
  in the **same transaction** as the state change (`Oban.insert/4` in an `Ecto.Multi`). A job whose
  `generation` is not the run's current one discards itself on claim. So at most one *current*
  pending batch exists, and an old one is inert.
- **Claim.** A batch begins with one conditional write —
  `UPDATE … SET claim_token = $t, claimed_at = now(), state = 'running' WHERE uuid = $u AND
  generation = $g AND claim_token IS NULL AND state IN ('queued','running')`. Zero rows: obsolete or
  duplicate delivery (discard), or a claim still held by a draining batch (snooze a few seconds).
- **Checkpoint.** One transaction, conditional on the claim (`claim_token = $t`): add the batch's
  progress **increments** (C7), store the cursor, release the claim, and — only if the returned
  state is still `running` — bump `generation` and insert the successor job. Whatever the state
  became meanwhile, the work already done is recorded.
- **`pausing` and `cancelling`.** Pause or cancel while a claim is held sets `pausing` /
  `cancelling`; the draining batch's checkpoint turns it into `paused` / `cancelled` and dispatches
  nothing. With no claim held they go straight to `paused` / `cancelled`. **Resume is refused while
  `pausing`** (the button is disabled with "current batch finishing") — this is what removes the
  pause→resume overlap. `pausing` and `cancelling` are *active* states in the partial unique index,
  so a **retry or a new run for the same kind and scope cannot start until the old one is terminal** —
  the cancel→retry overlap across run UUIDs.
- **Pause and cancel never touch Oban rows.** Not `Oban.cancel_job`: a pending job can become
  executing before the cancel reaches it, and cancelling an executing job kills it mid-batch. A
  pending successor of a paused/cancelled run simply claims, sees the state, and returns `:ok`.
- **`run_inline/3`** takes the same claim, under its own token, and refuses (`{:error, :claimed}`)
  when one is held; it checkpoints and fails by the same rules.

### R2 — An atomic protocol for completion and controls (C2)

Every transition is one transaction: the conditional run update, the Oban insert (if any), and the
Activity entry (`Activity.entry_changeset/1`, inserted in the `Multi`); the PubSub broadcast
(`Activity.broadcast/1` and the run topic) happens **after commit**. Nothing re-reads state and then
writes separately.

Precedence when the final batch returns `{:done, result}` — decided in the checkpoint transaction:

| State at the checkpoint | Result |
|---|---|
| `running`, `restart_requested` false | `completed` |
| `running`, `restart_requested` true | back to `queued`, counters/cursor reset, new generation, flag cleared **only if its value is the one this batch read** (a trigger that lands after is kept) |
| `pausing` | `completed` (nothing is left to pause); the run record notes "paused request arrived after the last batch" |
| `cancelling` | `cancelled` — the maintainer asked to stop; the result is recorded either way |

A recovered old Oban job cannot consume a newer checkpoint: it fails the generation test in R1.

**Side-effect contract.** A crash after external work and before the checkpoint replays that batch.
A kind declares `idempotent?/0`; the storage kinds are (reconcile, backfills re-check before acting).
A non-idempotent kind (a broadcast) must keep its own per-item marks and may not be started until it
does — the engine cannot supply that.

### R3 — `jobs.manage` is granted, never backfilled (C3)

`jobs` stays *view*. `jobs.manage` is an ordinary sub-permission, not backfilled to current holders.
Admin receives it through `auto_grant_new_keys_to_admin/0` at boot like every new key; Owner has
everything; a custom role that should control jobs is granted it in the permissions matrix.
**Decision needed from the maintainer:** is Admin getting it automatically what you want? (It is
the existing behaviour for any new key.)

### R4 — Controls take a Scope; the system is a separate door (C4)

- User controls: `Jobs.start(scope, kind, run_scope, opts)`, `pause(scope, run)`, `resume/2`,
  `cancel/2`, `retry/2`. Each checks `Scope.can?(scope, "jobs.manage")` **and** the kind's
  `permission/0` against the *active role* scope, and takes the audit actor from it.
- Trusted callers (boot, cron, a Mix task, a revision-bump trigger): `Jobs.System.start(kind,
  run_scope, mode: :auto | :cron | :script, source: "profile revision")`. A different function in a
  different module, so a missing actor in the first can never mean "system". `mode` is not a user
  option on the first door.
- The LiveViews pass `socket.assigns.phoenix_kit_current_scope`. A test proves an Owner whose active
  role is restricted cannot control through an actor-UUID reload.

### R5 — Recovery: terminal Oban states, a durable rescue budget (C5)

The sweeper reads the run's own Oban row (`oban_job_id`), not just "is there any job":

| Oban row | Run is `running`/`queued` | Action |
|---|---|---|
| `executing` | — | leave it (Lifeline owns a genuinely dead one, after 60 min > the 30-min batch timeout) |
| `available`/`scheduled`/`retryable` | — | leave it |
| `discarded` | — | the batch exhausted its attempts → run `failed`, `error` from the job's errors |
| `cancelled` outside the engine | — | run `failed` ("job cancelled outside the run") |
| `completed`, run still active, no successor | — | a lost dispatch → **rescue**: `rescues + 1`, new generation, dispatch |
| none (row pruned) | — | lost dispatch → rescue |

`rescues` is on the row, so the budget survives restarts; at the limit (default 3) the run is
`failed`. A stale `heartbeat_at` alone never triggers a rescue. A stale **claim** is released only
when the Oban row is not `executing` for a grace period.

### R6 — Honest draining, and purge is not controllable at first (C6)

- The UI says "Pause requested — the current batch is finishing" (with the claim's age) instead of
  implying a stop.
- `storage.purge_library` ships **visible but not pausable or cancellable** (`controls/0` returns
  `[]`): `Libraries.do_purge/1` loads and walks the whole library, deletion cannot be undone, and the
  `purging` marker deliberately refuses a restore. Batching the purge, and what cancelling one
  means, is its own piece of work after the engine ships.

### R7 — The batch callback checkpoints and delays together (C7)

```elixir
@callback batch(run) ::
            {:more, progress, opts}   # opts: [schedule_in: seconds]
            | {:done, result}
            | {:snooze, seconds}      # no checkpoint: waiting on something external
            | {:error, reason}        # counts against the Oban attempt

@type progress :: %{cursor: map(), done: non_neg_integer(), failed: non_neg_integer(),
                    total: non_neg_integer() | nil}   # done/failed are INCREMENTS of this batch
```

The engine adds the increments to the row inside the checkpoint transaction, so a replayed batch
cannot double-count. The final batch's increments are applied in the same transaction that
completes the run. `on_start/1` is validation only (no side effects, may refuse). `on_finish/2` runs
**after** the finishing transaction commits and must be idempotent. A kind sets its Oban `timeout`
through `timeout/1` (reconcile keeps 30 minutes).

### R8 — "Out of date" is not "eligible now" (C8)

Two queries, not one: `Reconciler.out_of_date_query/1` (revision mismatch, regardless of attempt or
processing windows — what library state counts) and `stale_query/0` (the work-selection query,
unchanged). Library state adds the **failing** count (files inside their ten-minute retry window)
and surfaces them as **Needs attention** instead of letting them fall out of the number. The healthy
badge reads **Up to date**, not "In sync", until `storage.verify` exists: matching revisions do not
prove every recorded object is still there.

### R9 — Rollout and acceptance (C13.3)

- **Shims are removed by evidence, not by the calendar.** The old workers' `perform/1` clauses stay
  until `mix phoenix_kit.doctor` finds no `oban_jobs` row for them; the release that removes them
  says so.
- **A kind that disappears** (module disabled or removed) with a live run: dispatch finds no kind and
  marks the run `failed` ("kind unavailable"), never loops; **Retry** works once the module is back.
- **Dead-queue and "no sweeper" warnings are observed, not inferred from local config:** the queue is
  suspect when no job of that queue has finished recently while runs are `queued`; the sweeper stamps
  `job_runs_last_sweep_at` (a settings row) each pass and the Runs tab warns when it is stale. A web
  node with `queues: false` says nothing about a separate worker node.
- **Phase 1 acceptance adds real-database concurrency and crash tests** — the eight Codex lists in
  §13.3 — alongside the pure state-machine tests: concurrent starts; pause→resume and cancel→retry
  during an executing batch; a trigger during the final batch; crashes around side effects,
  checkpoint and dispatch; final-attempt errors, timeouts and Lifeline discards becoming terminal;

- **Activity** is written in the transition's transaction (R2). Run history may expire after
  `activity_retention_days` while a run sits paused for longer; storage *configuration* entries

### 16.1 Findings to fix

#### F1 — BUG - HIGH: recovery decisions are made before the row lock

Locations: `lib/phoenix_kit/jobs/sweep_worker.ex:66`, `:124`, `:151`, `:158`;
`lib/phoenix_kit/jobs/state_machine.ex:197`.

The sweeper selects old run structs and reads their Oban jobs outside the transaction that
changes the run. `Engine.transition/3` subsequently locks and reloads the run, but neither the
`:rescue` nor the standalone `:fail` event verifies the generation, job id, age or claim used to
make the recovery decision. In particular, `:rescue` unconditionally clears a claim on a
`running` run. The row lock serializes the write; it does not validate the earlier observation.

**Reproduced with separate PostgreSQL connections:** a sweep reads generation 1's completed
job while another transaction rescues the run, creates generation 2 and claims it. After that
transaction commits, the stale sweep acquires the lock, clears generation 2's live claim, bumps
to generation 3 and dispatches another batch. Generation 2's Oban job is still `executing`.
Its later checkpoint is rejected, but its side effects can overlap generation 3's. A stale
`discarded`/`cancelled` observation can similarly fail a newer generation. Two sweeps can also
charge the rescue budget twice for one lost dispatch.

**Fix:** give recovery its own engine transaction. Lock the run, recheck its age and current
dispatch/claim, and read the current Oban job using the correct prefix. Require the observation's
generation/job id to remain current; make a stale observation a no-op. When releasing a dead
claim, condition the write on that token and dispatch. Refuse a generic rescue of a held claim.
Recheck job state as part of this protocol rather than trusting the initial candidate query.

**Regression:** gate a sweep after its snapshot, let another rescuer/worker advance and claim
the run, then release the sweep. Assert the live token and generation survive, no successor is
inserted, and the rescue count is not charged again. Repeat with a stale terminal Oban state.
This closes the remaining R1/R2/R5 violation.

#### F2 — BUG - HIGH: the sweeper steals a live inline batch

Locations: `lib/phoenix_kit/jobs/engine.ex:257`; `lib/phoenix_kit/jobs/sweep_worker.ex:90`, `:144`;
`lib/phoenix_kit/jobs.ex:270`.

An inline claim increments the generation but has no Oban job of that generation. Once its
`updated_at` is older than 120 seconds, the sweeper treats its missing/mismatched Oban row as
proof that the batch died, releases the claim and dispatches queued work. The original inline
process continues. This applies both to a newly created inline run and to one taken over from
an available queued dispatch. Capture-date batches are explicitly allowed ten minutes.

**Reproduced:** start without dispatch, take an inline claim, age the run, send a fresh heartbeat,
then sweep. The sweep releases the live token and inserts a new dispatch. The inline checkpoint
gets `:claim_lost`; another worker can claim immediately. `heartbeat/1` updates `heartbeat_at`
only, and neither the candidate query nor the recovery decision consults it.

**Fix:** record the execution owner independently of the start mode (`manual`/`script` is
attribution, not ownership). Define how a live inline owner is protected and how a dead one is
recovered: an explicit renewable lease with a replay/fencing contract, or another durable owner
mechanism. Until that exists, do not infer that an inline claim died from an absent Oban job.
Simply excluding all inline claims would prevent overlap but leave crashed scripts stuck; make
that limitation explicit if chosen as an interim solution.

**Regression:** hold a real inline batch past the grace threshold while sweeping; it must keep
its claim and have no concurrent successor. Also kill the inline owner and test the chosen
recovery policy. R1's inline guarantee is not met today.

#### F3 — BUG - HIGH: an obsolete dispatch can fail the current run when its kind disappears

Locations: `lib/phoenix_kit/jobs/run_worker.ex:53`, `:128`.

`perform/1` resolves the kind before taking the generation-checked claim. If resolution fails,
`unavailable/2` calls the unconditional `{:fail, message}` transition using only the run UUID.
Consequently an old job is no longer inert after a module is disabled/removed. It can fail a
newer generation and clear that generation's live claim, or turn a paused run into `failed`.
The active slot is then free even though the old batch may still be doing external work.

**Reproduced:** checkpoint generation 1, claim generation 2, remove the kind from the configured
registry, and perform generation 1's actual persisted job. The run becomes `failed`, generation
2 loses its claim, and its checkpoint is refused.

**Fix:** perform the generation/state/claim checks before any unavailable-kind mutation. Resolve
the kind from the claimed run and checkpoint its failure using the acquired token. Obsolete,
inactive and busy deliveries must retain their usual behavior regardless of kind availability.
Failing a genuinely current dispatch whose kind is gone remains the right R9 decision.

**Regression:** deliver an obsolete job with the kind unavailable against a newer live claim
and against a paused run; neither may change. A current unclaimed dispatch must still fail with
the clear unavailable-kind error. This is a direct contradiction of R1's obsolete-job rule.

#### F4 — BUG - HIGH: recovery queries the wrong Oban schema on named-prefix installs

Location: `lib/phoenix_kit/jobs/sweep_worker.ex:144`.

Dispatch correctly uses `Oban.insert/1`, which carries the configured Oban prefix. Recovery uses
`repo().get(Oban.Job, id)` without that prefix. `Oban.Job` has no PhoenixKit `@schema_prefix`, so
this reads the connection's default schema, normally `public`. On a named-schema-only install
the sweep raises because the table is absent; with a public install alongside it, it reads the
wrong jobs. A miss rescues healthy runs repeatedly until the budget is exhausted. An unrelated
row with the same integer id and generation can also influence the decision.

**Reproduced:** start Oban with a scratch schema prefix, insert a run's dispatch there and leave
it `available`. A raw public lookup cannot find it. After aging the run, the sweep nevertheless
rescues it and inserts a second generation while the healthy initial dispatch remains pending.
This probe isolates Oban query routing; it does not recompile the kit's schemas with a prefix.

**Fix:** read jobs through the configured Oban repo/prefix, following
`lib/modules/sitemap/scheduler_worker.ex:377`'s `Oban.Repo` pattern. Also check the row's
`run_uuid`/worker as well as its generation before treating it as the current dispatch. Handle
an unavailable local Oban instance explicitly for script/web-only callers. Apply the same
prefix correction to the Jobs page's direct Oban reads and `Jobs.get_job_stats/0`; those paths
predate this recovery defect but share the assumption.

**Regression:** exercise dispatch and sweep with non-public Oban storage, first with public
Oban rows present and then with no public Oban table. The full-chain migration oracle cannot
prove runtime query routing. R5 and supported named-prefix installs require this fix.

#### F5 — BUG - MEDIUM: inline execution drops snooze and batch delays

Location: `lib/phoenix_kit/jobs.ex:283`.

After every nonterminal checkpoint, `inline/3` immediately claims and invokes another batch.
It ignores both `{:snooze, seconds}` and `schedule_in:` on `{:more, progress, opts}`. A kind
waiting for an external service therefore loops through transactions and service calls without
the requested wait; its progress callback also fires on snoozes.

**Reproduced:** an inline kind returns `{:snooze, 3}` once and then completes. Both batches run
in less than 1.5 seconds. The same unconditional recursion drops `schedule_in:`.

**Fix:** honor the delay while preserving pause/cancel checks and the ownership policy in F2.
Use bounded waits if controls must remain responsive, and call progress callbacks only for
actual progress. Test both snooze and `schedule_in:` and a control received during the wait.
This is another gap in the inline parity promised by R1/R7.

#### F6 — BUG - MEDIUM: the documented Kind example reverses result and final progress

Locations: `lib/phoenix_kit/jobs/kind.ex:27`; `lib/phoenix_kit/jobs/run_worker.ex:113`.

The public callback is `{:done, result, progress}`, whereas the engine's normalized outcome is
`{:done, progress, result}`. The example returns `{:done, %{done: 0}, %{"imported" => run.done}}`,
using the engine ordering in a public kind. It stores `%{done: 0}` as the result and reads the
`"imported"` map as progress. Both are maps, so normalization silently accepts the mistake.

**Reproduced through `batch_outcome/3` and the state machine. Fix the example** to
`{:done, %{"imported" => run.done}, %{done: 0}}`. Document the internal ordering at the worker
boundary; a named result/progress structure would reduce future confusion. The proving storage
kind and the test Counter already use the correct public ordering. Also replace the Kind
moduledoc's snooze claim of "no checkpoint": the engine does release/checkpoint the claim and
dispatch a delayed successor, though it leaves progress unchanged.

#### F7 — BUG - MEDIUM: broadcasts and finish callbacks can run before an outer transaction commits

Locations: `lib/phoenix_kit/jobs/engine.ex:99`, `:198`, `:371`.

Returning from `repo().transaction/1` does not imply a commit when the engine is called inside
a host transaction or `Ecto.Multi` callback. The nested transaction joins the outer one.
`published/3` and `finished/2` then run before that outer transaction commits, contrary to R2
and the module documentation. A later host rollback removes the run/job/history while an event
has already been delivered or `on_finish` has already performed an external action.

**Reproduced:** subscribe to run events, call `Engine.start/3` in an outer transaction, receive
`:started` there, then roll the outer transaction back. The broadcast exists; the run does not.

**Fix:** either support outer transactions with a durable outbox/post-commit delivery mechanism,
or reject such calls before writing and document that callers must invoke Jobs after their
transaction commits. Do not advertise unconditional post-commit effects while silently allowing
the nested case. Add a rollback regression for start and a terminal transition.

### 16.2 Improvements worth carrying forward

#### I1 — IMPROVEMENT - MEDIUM: state the finish callback's delivery guarantee

`Engine.finished/2` is best effort: a crash after commit, a raised callback, or an unavailable
kind can permanently skip `on_finish/2`. An Oban retry sees a terminal run and does not replay
the callback. Idempotence alone does not provide delivery. Phase 1's capture-date callback is a
no-op, so durable completion delivery is not an additional release blocker. Document this now;
before a kind depends on completion cleanup/notifications, persist a pending effect and retry it
through an outbox or a separate worker. Lost PubSub events are acceptable only with a complete
periodic refresh fallback (see I4).

#### I2 — IMPROVEMENT - MEDIUM: make replay safety and progress guarantees explicit

`idempotent?/0` is required but is never called. R2 says a kind may not start until replay is
safe. Validate that declaration at the shared start boundary, or explicitly describe it as
informational; a kind with durable per-item deduplication can declare effective replay safety.
Do not imply that the engine enforces a property it does not inspect.

Also, **code-derived limitation, not exercised by a process-kill probe here:** the capture-date
kind selects only files whose `taken_at` is nil. A crash after dating some files but before
checkpoint means replay skips those files, so their side effects are safe but their counters
and outcome totals are never credited. A first-batch replay also recomputes `total` from the
smaller pending set. Later-batch replays can leave a completed run below its recorded total.
Either keep durable per-item/batch accounting or describe recovered counts as approximate in
the UI and CLI. Add the missing crash-between-side-effect-and-checkpoint test with assertions
about both file state and progress; do not assert only that no file is dated twice.

#### I3 — IMPROVEMENT - MEDIUM: use the core form primitives in the new filters

`index.html.heex:85` and `:101` introduce raw selects with `label-text`, `select-bordered` and
the old form-label use of `.label`, despite the component guide and workspace daisyUI 5 audit.
The first two classes are dead in v5; neither label is wired to its select. Replace these new
filters with `Core.Select`, keeping the existing unique form ids and URL-state events. This is
a small fix that avoids repeating the adoption gap recorded in the workspace instructions.

#### I4 — IMPROVEMENT - MEDIUM: finish the periodic refresh and global health checks

`Index.handle_info(:refresh)` refreshes the table but omits `load_selected_run/1`. If a worker
dies after committing its checkpoint and before broadcasting, an open run modal retains its
old state/history indefinitely even while the periodic refresh updates the table. Reload the
selected run on that timer and test a DB transition with no broadcast.

The sweeper warning and Runs badge are also computed from the current filtered page, rather
than all active runs. Filtering to completed runs or paging past the active rows hides the
warning; paused runs count as waiting although the sweep deliberately leaves them alone.
Use a separate global count of states the sweep actually services for the health warning,
and define whether the badge is a global active count or a count of this view.

### 16.4 Answers to the handoff's seven questions (§4)

1. **Start retries:** the code returns `{:error, :raced}` after three exhausted attempts; it
   does **not** return the last seen run in that case. Three is a reasonable bounded policy if
   callers retry or surface that error. Do not silently claim the trigger was recorded.
   `existing/3:149` still turns other restart-transition errors into `:existing`; propagate
   those errors too. A per-kind/scope advisory lock is an alternative if repeated finish/start
   contention becomes common, not a prerequisite to shipping this phase.
2. **Recovery versus a slow living batch:** the stale checkpoint token fences the eventual
   database checkpoint only. It does not fence external work. The genuine partition/Lifeline
   case needs the documented replay contract, but F1/F2/F4 cause overlap even without a
   partition. Fix those first. For future non-idempotent kinds, use durable per-item claims or
   an external fencing/idempotency mechanism; a token check after the effect is too late.
3. **Heartbeat:** keep it as observability and a cooperative lost-claim check. Correct
   `Jobs.heartbeat/1`'s documentation, which currently says silent batches influence sweeper
   recovery. Do not use stale heartbeat alone to steal a queued worker's claim. Whether it
   participates in an explicit inline lease is part of F2, with a different ownership contract.
4. **Stale controls:** acceptable. Sharing authorization, then rechecking state under the
   engine lock and returning a flash, is the right behavior. The active-role check holds.
5. **Activity grain:** keep semantic transitions, not one entry per batch. The transactions
   preserve useful audit history without overwhelming the feed. Progress belongs on the run
   row and PubSub. F7 is about when effects escape, not the choice of audit grain.
6. **System door:** keep it public and documented as trusted application code. `@doc false`
   or a config flag does not create an authorization boundary for code already running in
   the VM. User paths must keep passing Scope to the authorized door; preserve the separate
   system entry point and state the same trusted-caller assumption for `run_inline/3`.
7. **Unavailable kind:** fail a current, unclaimed dispatch with a clear error, as R9 says;
   retry when the kind returns. Pausing instead is not needed. F3 must ensure obsolete,
   inactive or already-held deliveries cannot use that policy to invalidate another batch.

The declared scope exclusions remain accepted: no purge kind, no phase-2 library health or
reconcile, no phase-3 storage audit, no failure notifications. Deferring the dead-queue warning
is acceptable when the observed sweeper warning is accurate; keeping the legacy shims until
doctor evidence exists follows the maintainer's decision.

## 18. Codex recheck of the phase 1 fixes — 2026-10-03

Reviewed `0f8987c2f` against §16 and Claude's response in §17. **The original live-claim,
obsolete-delivery and running-instance prefix failures are fixed.** Recovery now makes its
decision under the run lock, the worker claims before resolving the kind, and the engine refuses
an outer caller transaction. The new regression coverage is useful, including Owner scope,
queued/inline claim concurrency, timeout and Lifeline recovery. There are four remaining MEDIUM
issues below; I would resolve R1–R3 before giving the engine a clean release verdict.

### 18.1 Remaining findings

#### R1 — BUG - MEDIUM: an inline delay still looks like a lost dispatch

Locations: `lib/phoenix_kit/jobs.ex:302`, `:309`;
`lib/phoenix_kit/jobs/state_machine.ex:255`;
`lib/phoenix_kit/jobs/sweep_worker.ex:135`.

The lease protects an inline batch while it holds a claim. A successful nonterminal checkpoint
clears both `claim_token` and `claim_owner`, increments the generation and inserts no successor
because inline execution passes `dispatch: false`. The calling process then waits for
`schedule_in:` or a snooze. Once that wait exceeds the 120-second grace period, recovery sees
an unclaimed run with no current dispatch and enqueues another batch immediately. It has no
durable record of the inline owner or the requested next-batch time during this wait.

**Reproduced:** an inline Counter asks for a 600-second delay after its first batch. During the
wait, age the checkpoint row past the sweep grace period and sweep. The sweep records a rescue
and creates an `available` Oban job. Draining that queue completes the next batch immediately,
while the original inline caller was still observing its requested delay. This is a time-window
probe, not a real ten-minute sleep. The row lock still prevents two batches from taking the
same claim; the defect is premature work, an unnecessary rescue charge and loss of inline
execution semantics. Short one-second delay tests cannot establish this case.

**Fix:** retain durable inline ownership between batches, and record the earliest next-batch
time. Protect a living inline wait with its owner/lease; if recovery legitimately takes it over,
carry the remaining delay into the dispatch. Keep pause/cancel responsive. Do not fix this by
holding the *batch* claim throughout a wait, which would make a pause appear to drain work that
is not executing. Add a wait longer than the sweep grace period to the recovery tests and assert
that no early successor is created or executed. F2/F5 are therefore only partly closed.

#### R2 — BUG - MEDIUM: unavailable Oban reads fall back to the public schema

Locations: `lib/phoenix_kit/jobs/oban_store.ex:45`, `:49`, `:54`, `:75`.

With a running Oban instance, the prefix fix works and the dispatch identity checks are correct.
Without one, the page/stat helpers fall back to raw `repo().all/one/aggregate` queries. They
again read the connection's default schema. `with_config/1` also maps any configured-query
failure to `:unavailable`, so a failure reading the correct table can silently produce results
from a different table.

**Reproduced:** with a prefixed instance running, query a dispatch id and get the prefixed
`RunWorker` row. Stop that instance, leaving a `Public.Decoy` row with the same id in public.
The same `ObanStore.all/1` and `one/1` now return the decoy. The dispatch lookup correctly returns
`:unavailable`, but page/detail/count reads silently switch storage. In a named-schema-only
installation, the fallback can instead raise because the public table is absent.

**Fix:** use a known, validated Oban configuration even when the local supervisor is absent,
or return explicit unavailable/empty defaults and show unavailable queue data. Never infer a
prefix by falling back to a raw query. Distinguish missing local configuration from a database
query failure. Add no-instance coverage for list, detail and counts alongside the existing
running-instance prefix tests. F4 is not completely closed for the documented script/web-only
case.

#### R3 — BUG - MEDIUM: a run with no dispatch can exhaust its rescue budget with no Oban available

Locations: `lib/phoenix_kit/jobs/oban_store.ex:28`;
`lib/phoenix_kit/jobs/sweep_worker.ex:135`;
`lib/phoenix_kit/jobs/engine.ex:460`.

`dispatch_of/1` returns `nil` immediately for a nil job id, before checking whether Oban can
be asked. Such a run bypasses the conservative `:unavailable` recovery branch. A manually
invoked sweep on a script/web-only process therefore charges a rescue and increments the
generation even though insertion again has no Oban instance and creates no job. Repeated
passes eventually fail the run for lost dispatches that were never made.

**Reproduced:** stop Oban, start a run (its `oban_job_id` is nil), then age and sweep it four
times. The first three passes each report one rescue with no job inserted; the fourth marks
the run failed with `rescues: 3`. This uses the public manual sweep entry point, not a cron
worker running without its supervisor. It contradicts §17's statement that an unavailable
Oban instance leaves the run alone.

**Fix:** establish dispatcher/configuration availability before consuming the rescue budget,
including the nil-id case. Leave an orphan queued while dispatch is impossible; rescue it once
when a usable instance returns. Add a regression proving that repeated sweeps without an
instance preserve the budget, then start Oban and assert one successful recovery. This is the
other remaining F4/recovery availability gap.

#### R4 — BUG - MEDIUM: the approximate-count notice misses ordinary crash retries

Location: `lib/phoenix_kit_web/live/modules/jobs/runs_components.ex:208`.

The notice is gated on `run.rescues > 0`. A batch whose Oban job becomes available/retryable
after a crash has its claim released and reuses that dispatch; it does not increment `rescues`.
Its counts can nevertheless omit already-completed side effects. Completion clears the error,
so the drawer can present those recovered counts without the new explanation.

**Evidence:** the permanent capture-date crash test dates two files before checkpoint and
finishes with only one credited file. It takes the release/retry path, not a dispatch rescue.
An additional probe confirmed that this recovery completes with `rescues: 0` and `error: nil`;
the drawer condition remains false. The Mix task's new caveat is in its help documentation,
not its ordinary progress/result output.

**Fix:** record interrupted/replayed batches separately from lost-dispatch rescues, and use
that durable marker for the notice and CLI caveat. Alternatively, disclose approximate counts

### 20.1 Remaining cases

#### G1 — BUG - MEDIUM: another inline caller can bypass a living owner's saved wait

Locations: `lib/phoenix_kit/jobs/engine.ex:303`, `:338`;
`lib/phoenix_kit/jobs/state_machine.ex:94`.

Keeping `claim_owner: "inline"` between batches now protects the wait from the sweeper.
It does not protect the wait from `Jobs.run_inline/3`/`Engine.claim_inline/1`. Claiming checks
only whether `claim_token` is present, and the batch checkpoint intentionally cleared that
token. There is no identity for the still-living inline owner, and no check of the saved
`wake_at` before another inline caller claims the run. The claim clears `wake_at`.

**Reproduced:** start an inline run with two steps, checkpoint its first batch with a
600-second wait, then call `Jobs.run_inline/3` again for the same kind/scope. The second call
returns a completed run immediately, with `done: 20`, while the original owner's lease and
next-batch time are still valid. No overlap of batch claims is needed to violate the delay.

**Fix:** enforce ownership at the inline claim boundary, not only in recovery. Give an inline
invocation a durable owner token carried between batches; a different invocation must refuse
while that owner is live, or safely take over while preserving the pending wait. Let the
original invocation reclaim its next batch through its owner identity. At minimum, no caller
may silently discard a future `wake_at`. Preserve immediate pause/cancel and expired-owner
recovery. The new regression expects the second caller to be refused as `:claimed`.

#### G2 — BUG - MEDIUM: a second rescue forgets the queued run's pending delay

Locations: `lib/phoenix_kit/jobs/state_machine.ex:211`, `:362`.

The first rescue computes `Run.seconds_until_wake(run, now)` from the old row and schedules
its replacement correctly. Its changes also merge `release()`, which sets `wake_at: nil`.
If that replacement dispatch is lost before it runs, a second rescue has no next-batch time
left on the run and schedules work immediately.

**Reproduced:** checkpoint a queued run with a 600-second delay, remove its current job,
age the run and sweep; repeat the lost-dispatch/sweep sequence once. The second replacement's
`scheduled_at` is earlier than the original due time. The existing test verifies only the
first rescue, so it misses the loss of the durable scheduling marker.

**Fix:** preserve `wake_at` when rescuing an unclaimed delayed run, until a batch claims it
or a control intentionally clears the delay. Separate releasing a batch claim from clearing
all scheduling metadata. Test repeated rescue within the budget, not only the first dispatch.
This is the remaining delayed-queued-work portion of R1.

#### G3 — BUG - MEDIUM: an expired inline wait still charges a rescue without Oban

Location: `lib/phoenix_kit/jobs/sweep_worker.ex:153`.

R3's nil-job-id availability check now protects ordinary waiting queue runs. The new
inline-waiting clause runs before the `ObanStore.dispatch_of/1` availability check and directly
returns `{:rescued, {:rescue, limit}}` for an expired lease. With no Oban instance it still
increments `rescues`/`generation`, clears ownership and inserts no replacement job.

**Reproduced:** create an inline run between batches, backdate its heartbeat and wake time
beyond the lease, and sweep without starting Oban. Expected: no rescue charged while dispatch
is unavailable. Actual: `rescued: 1`, with no job inserted. Subsequent passes see the cleared
owner and take the corrected ordinary unavailable branch, so this is one wasted rescue charge
per such takeover, not the earlier unlimited sequence for a plain queued orphan.

**Fix:** require dispatch availability in this inline-waiting recovery branch too. An expired
owner may be released without charging a dispatch rescue, but do not count a replacement that
cannot be made. Preserve the budget until a usable dispatcher returns; then recover once.
This is the remaining R3 gap.
